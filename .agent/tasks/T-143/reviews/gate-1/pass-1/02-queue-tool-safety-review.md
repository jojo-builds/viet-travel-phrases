# Gate 1 Pass 1: Queue Tool Safety Review
## Summary
This direction is safe before edits if recovery-handoff generation is added as a bounded, explicit maintenance path and not folded into the existing cheap repair or desktop restart flows. Today `repair` is intentionally limited to reclaimable normalization plus `queue-index.json` rewrite (`E:\AI\SpeakLocal-App-Family\.agent\queue_tool.py:1277-1308`, `E:\AI\SpeakLocal-App-Family\.agent\QUEUE_REPAIR.md:19-21,37-42`), and `desktop-recover` is limited to app start/restart plus optional ledger updates (`E:\AI\SpeakLocal-App-Family\.agent\queue_tool.py:1312-1434`, `E:\AI\SpeakLocal-App-Family\.agent\QUEUE_MAINTENANCE.md:67-90`). That separation is worth preserving.

## Key Risks
- Do not hide recovery-task creation inside `repair`. That would violate the current low-cost repair contract and turn a routine normalization pass into task authoring (`E:\AI\SpeakLocal-App-Family\.agent\QUEUE_REPAIR.md:3-4,19-21,37-42`; `E:\AI\SpeakLocal-App-Family\.agent\queue_tool.py:1277-1308`).
- Do not overload `desktop-recover` to create handoffs. Its current surface is restart/start plus ledger only; mixing task creation into that command would widen side effects in a surprising way (`E:\AI\SpeakLocal-App-Family\.agent\queue_tool.py:1312-1434,1903-1908`).
- The eligibility rule must be narrower than “all blocked” or “all reclaimable.” `classify_task()` treats all `blocked` tasks as terminal and stale `in_progress` tasks as reclaimable (`E:\AI\SpeakLocal-App-Family\.agent\queue_tool.py:662-709`), but the example interrupted tasks are already `blocked` with `phase: interrupted-awaiting-recovery` (`E:\AI\SpeakLocal-App-Family\.agent\tasks\T-139\state.json:4-5`, `E:\AI\SpeakLocal-App-Family\.agent\tasks\T-140\state.json:4-5`). Without a dedicated interrupted-task predicate, the generator could create bogus handoffs.
- Preserve the original task as history. The spec requires a new task id/folder and says the interrupted original must remain historical truth (`E:\AI\SpeakLocal-App-Family\.agent\tasks\T-143\spec.md:61-64,83-89`). The implementation must not repurpose the original task in place or silently move it back to `queued`/`in_progress`.
- Keep runtime writes tightly scoped. Existing task metadata points at external worktree artifacts (`E:\AI\SpeakLocal-App-Family\.agent\tasks\T-139\state.json:39-44`, `E:\AI\SpeakLocal-App-Family\.agent\tasks\T-140\state.json:39-44`), and helper path resolution accepts absolute paths (`E:\AI\SpeakLocal-App-Family\.agent\queue_tool.py:472-476,726-735`). Recovery generation must not copy or write those paths; runtime writes should stay limited to queue-tooling surfaces and the new recovery task metadata.
- Enforce duplicate avoidance and task-id allocation under the queue mutation lock. The duplicate check must happen after a fresh reload while locked, or repeated maintenance runs can stamp out twin recovery tasks (`E:\AI\SpeakLocal-App-Family\.agent\queue_tool.py:570-606,1596-1617`; `E:\AI\SpeakLocal-App-Family\.agent\tasks\T-143\spec.md:83-90`).
- Keep the command surface narrow. The wrapper currently just forwards args into the Python parser (`E:\AI\SpeakLocal-App-Family\.agent\Invoke-SpeakLocalQueueTool.ps1:1-45`; `E:\AI\SpeakLocal-App-Family\.agent\queue_tool.py:1891-1936`). Avoid adding arbitrary path inputs, shell snippets, or PowerShell-mediated file creation.

## Recommendation
Proceed with an explicit maintenance-side recovery-handoff command or flag that has a true dry-run/inspection mode, leaves `repair` and `desktop-recover` semantics unchanged, creates only a new recovery task plus minimal backlink metadata, and refuses to act unless the original task is explicitly recognized as an interrupted meaningful task with no existing recovery handoff.

Approval: APPROVE
