## Outcome

T-160 designed the long-term offline SQLite architecture for SpeakLocal. It did not implement runtime SQLite. It created the plan that lets us move from scattered JSON/hand-coded page behavior toward one compiled offline phrase graph per language pack.

## What We Learned

The current app has several different concepts that look similar but are not the same:

| Current surface | Count | Meaning |
| --- | ---: | --- |
| Catalog families | 900 | Current intent/grouping unit |
| Phrase rows | 919 | Actual playable phrase rows |
| Authored rich pages | 163 | Current deep article/listing pages |
| Audio manifest entries | 3,756 | Lookup keys/usages/text mappings |
| Audio files | 2,427 | Actual bundled MP3 files, about 65 MB |

The weird counts are not automatically duplicates. They reflect different layers: family/grouping, phrase, page, audio usage, and actual audio asset.

## Product Meaning

Jojo's mental model is now the intended architecture:

- a phrase is the atomic learner-facing unit;
- every phrase should be page-capable;
- every phrase opens one canonical phrase page;
- page richness is a completeness/status field, not permission to have a page;
- old "family" behavior becomes `phrase_cluster`, a relation/grouping concept;
- search, browse, practice, and related rows should all route to the same canonical page.

This supports the Wikipedia-style phrase graph Jojo wants.

## Decisions Locked In

- SQLite should be a build-time generated bundled read model, not the authoring surface.
- Runtime remains fully offline.
- Bundled content DB is read-only; mutable local progress belongs in a separate app-container store.
- `phrase_page` is canonical; `page_alias` preserves old IDs and avoids duplicate pages such as duplicate `Chào anh`.
- `audio_asset` and `audio_usage` should distinguish the MP3 file from where/how the app uses it.
- Practice should reuse phrase graph IDs instead of creating a separate learning-content model.
